# ORION — Integration Hardening & End-to-End Verification

## Objective

Do NOT add new major features.

Do NOT redesign the architecture.

Do NOT change the v3.3 risk engine.

Do NOT modify golden expected values.

The goal of this task is to prove that the existing ORION components work together as one end-to-end cyber-intelligence pipeline.

## Step 0 — Inspect

Read:

* `AGENTS.md`
* `ORION_Master_Project_Documentation_v3.3.md`
* `risk_config.yaml`
* `docs/PHASE_STATUS.md`
* existing backend tests
* existing frontend structure

Inspect the current implementation before editing anything.

## Step 1 — Establish baseline

Run:

```bash
cd backend
pytest -q
```

and:

```bash
cd frontend
npm run build
```

Record failures before making changes.

Do not modify tests simply to make them pass.

## Step 2 — Verify phishing → alert

Use a realistic phishing message containing:

* brand impersonation
* suspicious domain
* credential request
* urgency language

Verify:

INPUT
→ DETECT
→ CLASSIFY
→ SCORE
→ EXPLAIN
→ ALERT
→ RESPOND

Verify that the generated alert is actually persisted.

Verify:

```text
severity >= MEDIUM
OR
assessment == inconclusive
```

creates an alert.

Explicitly test an inconclusive incident.

## Step 3 — Verify canonical incident

Inspect the generated incident.

Confirm it contains:

* incident_id
* module
* layer
* threat_type
* assessment
* severity
* risk_score
* confidence
* risk_breakdown
* evidence
* evidence contributions
* explanation
* recommended_actions
* entities
* model_metadata

Verify the explanation invariant:

Every explanation factor evidence_id MUST exist in incident.evidence.

## Step 4 — Verify authentication correlation

Create an authentication event using an entity that appeared in the phishing incident.

Example:

```text
user: ceo@example.com

5 failed logins within 5 minutes
followed by successful login
new device
new location
```

Verify that the authentication detector generates a separate incident.

## Step 5 — Verify automatic entity correlation

Do NOT manually create the relationship.

Verify that ORION automatically:

1. extracts the entity
2. canonicalizes it
3. persists it
4. finds the related incident
5. assigns the same correlation_id
6. stores related_incident_ids

The relationship must originate from actual persisted incident/entity data.

## Step 6 — Verify attack constellation

Verify that the frontend graph/constellation is generated from the actual correlation data.

Do not create decorative/static graph relationships.

Minimum acceptable chain:

```text
PHISHING
   ↓
shared entity
   ↓
ACCOUNT TAKEOVER
```

If a third real correlated incident already works, verify:

```text
PHISHING
   ↓
ACCOUNT TAKEOVER
   ↓
SESSION/SYSTEM ANOMALY
```

## Step 7 — Verify simulated response

For a detected incident, execute one recommended response through the existing simulation endpoint.

Verify:

* action status becomes `simulated`
* `simulated_at` is recorded
* ACTION_LOG is created
* INCIDENT_HISTORY is updated
* `automated == false`
* no real external action occurs
* incident lifecycle status is not automatically changed to resolved

## Step 8 — Add regression tests

Only after manually understanding the existing behavior, add focused tests for:

1. alert threshold
2. inconclusive alert
3. entity persistence
4. cross-module correlation
5. related incident retrieval
6. simulated action logging
7. explanation evidence invariant

Do not rewrite unrelated tests.

## Step 9 — Frontend verification

Confirm AnalyzeTab visibly presents:

```text
INPUT
→ DETECT
→ CLASSIFY
→ SCORE
→ EXPLAIN
→ ALERT
→ RESPOND
```

Verify that the alert shown in the UI corresponds to the backend-generated alert.

Do not generate a fake alert ID solely for presentation.

## Step 10 — Phase status

Only after all verification succeeds, update:

`docs/PHASE_STATUS.md`

so that status reflects demonstrated implementation rather than file/code existence.

Include concrete evidence for each passed criterion.

## Acceptance Criteria

This task is complete only when the following works end-to-end:

```text
Real phishing input
      ↓
Real detector
      ↓
Real evidence
      ↓
Canonical incident
      ↓
Risk engine
      ↓
Persisted alert
      ↓
Entity extraction
      ↓
Real authentication event
      ↓
Second incident
      ↓
Automatic correlation
      ↓
Attack constellation
      ↓
Simulated response
      ↓
Action audit trail
```

At the end report:

1. tests before changes
2. changes made
3. tests after changes
4. exact end-to-end scenario verified
5. correlation evidence
6. alert evidence
7. response simulation evidence
8. remaining gaps

Do not claim a phase passed unless its acceptance criteria were actually demonstrated.
